# ADR-0030: 배포는 EC2 1대 블루-그린에서 웹 2대 + 스케줄러 1대 롤링 배포로 전환한다

- 상태: 승인됨
- 날짜: 2026-09-14
- 관계: [ADR-0020](0020-managed-service-deployment.md)(관리형 서비스로 상태 분리)·[ADR-0021](0021-continuous-deployment.md)(CD 자동화)의 큰 방향(상태는 인스턴스 밖, 배포는 자동, SSH 없이 SSM)은 그대로 유지한다. 이 ADR이 대체하는 것은 ADR-0021 §결정 5·6이 정의한 **"블루-그린 가중치 전환" 메커니즘뿐**이다. ADR-0014(코인 감시 락)·ADR-0015(조회 캐시 락)이 이미 전제해 온 "다중 인스턴스 전환"을 실제로 상시화하는 문서이기도 하다.

## 맥락

웹서버를 다중 인스턴스 환경으로 확장하기로 하면서, 이 기회에 두 가지를 함께 결정했다.

1. **AWS 콘솔 수동 설정 대신 Terraform으로 코드화한다.** ADR-0020 §결과가 스스로 지적한 "콘솔 설정이 문서에만 있어 복원 불가능" 문제를 인프라를 다시 손대는 김에 해소한다 — 인스턴스가 여러 대로 늘면 콘솔 클릭만으로 설정을 일관되게 유지하기는 더 어려워진다.
2. **웹서버를 진짜 다중 인스턴스(2대, 동시에 트래픽을 받는 이중화)로 전환한다.** 지금까지의 "블루-그린"은 EC2 **한 대** 안에서 포트만 다른 컨테이너 두 개를 번갈아 띄우는 무중단 배포 기법이었다 — 인스턴스 장애 자체에 대한 이중화는 아니었다. ADR-0020 §6이 "상시 다중 인스턴스 운영은 별도 결정"이라고 미뤄 둔 그 결정이 이번이다.

### 블루-그린 전환 메커니즘은 "웹 2대가 항상 라이브"와 근본적으로 다른 모델이다

기존 `.github/workflows/deploy.yml`은 ALB 리스너 하나에 blue·green 두 타깃 그룹을 가중치(0/100)로 나눠 붙이고, 배포 때마다 그 가중치를 뒤집는 방식이었다(ADR-0021 §결정 5). 이 모델은 "인스턴스 하나, 색깔 둘"을 전제한다 — 웹 서버가 물리적으로 2대가 되면 "타깃 그룹 하나에 인스턴스 2개가 동시에 등록돼 둘 다 트래픽을 받는" 구조와 맞지 않는다. 가중치 전환을 인스턴스 2대에 그대로 적용하려면 타깃 그룹이 4개(각 인스턴스마다 blue/green)로 늘고, 그중 정확히 2개(각 인스턴스의 라이브 색)에만 가중치를 몰아주는 조합을 관리해야 해서, 복잡도가 인스턴스 수만큼 배로 늘어난다.

### 스케줄러 전용 인스턴스는 애초에 ALB 대상이 아니다

배치 작업(뉴스 수집·랭킹 재구성·코인 감시·주식 캔들 수집)과 빗썸 시세 피드를 트래픽 서빙과 분리된 전용 인스턴스에서 돌리기로 했다(웹 인스턴스의 HTTP 처리 용량과 배치·LLM 호출의 CPU/메모리 사용을 서로 침범하지 않기 위해서). 이 인스턴스는 ALB에 등록되지 않으므로 블루-그린이든 롤링이든 배포 전환 로직 자체가 필요 없고, 그냥 이미지만 교체하면 된다.

### 인스턴스가 늘면서 새로 생기는 두 가지 코드 문제

인스턴스가 1대에서 3대(웹 2 + 스케줄러 1)로 늘면서, 지금까지 "인스턴스 1대"를 암묵적으로 전제해 온 코드 두 곳이 문제가 될 수 있었다 — 이 ADR 이전에 각각 별도 이슈로 먼저 고쳤다.

- 빗썸 WebSocket 피드(`BithumbFeedLifecycle`)가 뜨는 인스턴스마다 독립적으로 연결을 열어, 인스턴스 수만큼 빗썸 쪽 레이트리밋 위험이 커지는 문제 — Redis 기반 리더 선출로 고쳤다(이슈 #564, PR #566).
- `StockReplaySessionScheduler`의 재생세션 확정 배치가 분산 락 없이 find-or-create 패턴으로만 동작해, 다중 인스턴스가 동시에 같은 배치를 타면 진 쪽이 처리되지 않은 예외를 던지는 문제 — `StockCollectionLock`과 같은 패턴의 락을 추가해 고쳤다(이슈 #565, PR #567).

그 외 기존 `RedisLock` 기반 배치들(`RankingRebuildLock`·`CryptoWatchLock`·`StockCollectionLock`)과 지정가 체결의 다중 인스턴스 중복 시도 허용(ADR-0024 §결정 5)은 이미 다중 인스턴스를 전제로 설계돼 있어 추가 조치가 필요 없었다.

## 결정

**웹 EC2 2대(둘 다 항상 ALB 타깃 그룹 하나에 등록돼 동시에 트래픽을 받는다) + 스케줄러 EC2 1대(ALB 미등록)로 간다. 배포는 롤링(한 대씩 순차로 등록 해제 → 배포 → 재등록)으로 한다. 인프라 전체는 Terraform(`infra/terraform/`)으로 코드화한다.**

```
                     ┌─ ALB (ACM 인증서, HTTPS) ─┐
                     │                            │
              [Target Group: web (1개)]
                     │              │
              EC2 web-1        EC2 web-2         EC2 scheduler (ALB 미등록)
                     └──────────────┴──────────────┘
                                 │  (상태는 인스턴스 밖에만 있다 — ADR-0020 유지)
                  ┌──────────────┼──────────────┬───────────────┐
                RDS          ElastiCache        S3          CloudFront
             (MySQL)          (Redis)      (업로드+프론트)   (www.finplay.site)
```

### 1. 타깃 그룹은 웹 인스턴스 수와 무관하게 1개다

blue/green 두 타깃 그룹을 없애고, 웹 인스턴스 전부를 타깃 그룹 하나에 등록한다. "라이브 색 판별"이라는 개념 자체가 사라진다 — 등록된 인스턴스는 전부 항상 라이브다.

### 2. 배포는 롤링이다 — 한 대씩 등록 해제 → 이미지 교체 → 재등록

GitHub Actions에서 `strategy.matrix`(`max-parallel: 1`)로 웹 인스턴스 목록을 순회한다.

1. 그 인스턴스를 타깃 그룹에서 `deregister-targets` → draining 대기
2. SSM Send Command로 새 이미지 pull + `docker compose -f compose.deploy.yaml up -d` + 컨테이너 헬스체크 대기 (기존 블루-그린 스크립트의 SSM·헬스체크 패턴을 그대로 재사용한다)
3. `register-targets` → ALB 타깃 헬스 대기
4. 실패 시 그 인스턴스만 실패 처리하고 멈춘다(`fail-fast`) — **아직 손대지 않은 나머지 인스턴스가 계속 트래픽을 받고 있으므로 그 자체로 무중단이 유지된다.** 블루-그린의 "실패 시 전환하지 않는다"(ADR-0021 §결정 6)와 목적은 같지만, 여기서는 "인스턴스를 아직 안 건드렸다"는 사실 자체가 안전장치다.

스케줄러 인스턴스는 별도 job으로 ALB 관련 단계 없이 이미지만 교체한다.

### 3. `compose.deploy.yaml`을 소스 빌드에서 이미지 참조로 바꾼다

기존 `compose.deploy.yaml`은 `build: context: .`로 EC2에서 직접 소스를 빌드하는 수동 배포 폴백용이었다. 이제 이 파일이 웹 2대·스케줄러 1대 전부의 **정상 배포 경로**가 되므로, `compose.bluegreen.yaml`이 이미 그랬듯 `image: ${APP_IMAGE}`로 바꿔 러너가 빌드해 ECR에 올린 이미지를 그대로 pull하게 한다 — EC2마다 다른 소스로 빌드되는 것을 막기 위해서다(ADR-0021 §맥락과 같은 이유).

### 4. 시크릿은 EC2에 수동으로 넣던 `.env` 대신 SSM Parameter Store에 둔다

`/finplay/prod/<KEY>` 이름 체계의 SecureString 파라미터로 옮긴다. Terraform이 값 자체를 아는 것(DB 접속 정보 등)은 직접 쓰고, 서드파티 시크릿(OPENAI_API_KEY 등)은 파라미터 "이름"만 선언해 Terraform state에 원문이 남지 않게 하고 `scripts/put-secrets.sh`로 사람이 1회 채운다. 각 EC2는 부팅 시점(그리고 필요하면 SSM Send Command로 언제든)에 `/opt/finplay/refresh-env.sh`가 이 값들을 읽어 `.env`를 만든다 — "EC2가 `.env`의 정본"이라는 기존 원칙(ADR-0021 관련 실무)을 유지하되, 그 정본을 만드는 절차를 코드화했다.

### 5. CloudFront + S3를 이번 인프라 범위에 포함한다

프론트(`finplay-frontend` 레포)의 정적 호스팅(S3 + CloudFront, `www.finplay.site`)도 같은 Terraform으로 관리한다. API는 그대로 ALB가 받는다 — 두 경로(정적 사이트는 CloudFront, API는 ALB)는 실제 운영 중이던 아키텍처를 그대로 반영한 것이다. CloudFront용 ACM 인증서는 AWS 제약상 리전 고정 원칙(`ap-northeast-2`)과 별개로 항상 `us-east-1`에 있어야 한다.

### 6. CloudWatch로 최소한의 관측성을 확보한다

EC2에 CloudWatch Agent를 설치해 메모리·디스크 사용률(기본 EC2 메트릭에 없는 값)을 수집하고, 컨테이너 로그는 Docker의 `awslogs` 드라이버로 직접 CloudWatch Logs에 보낸다. 디스크 사용률 알람은 `deploy/cd-runbook.md`에 기록된 실제 사고(2026-08-24, 이미지 태그 누적으로 디스크 100%)의 재발 방지가 목적이다. RDS·ElastiCache·ALB 기본 지표에도 알람을 걸되, **SNS 알림 연동은 지금 하지 않는다** — 알람 자체는 만들고 콘솔에서 상태만 확인하며, `alarm_actions` 변수를 비워 둬서 나중에 SNS 토픽 하나만 추가하면 전체 알람에 이메일 알림이 붙게 설계했다.

## 근거

- 인스턴스 장애·과부하에 대한 진짜 이중화(다중 인스턴스)와 배포 무중단(블루-그린)은 서로 다른 문제다. 이 저장소는 지금까지 후자만 갖고 있었다. 전자를 얻으려면 "인스턴스가 여러 대"라는 전제를 인프라와 배포 파이프라인 양쪽에 반영해야 한다.
- 타깃 그룹을 인스턴스 수만큼(또는 그 배로) 늘리는 대신 하나로 유지하고 롤링 배포로 가는 편이, AWS가 이미 타깃 그룹 단위로 제공하는 등록/해제·헬스체크 기능을 그대로 쓰면서 복잡도를 인스턴스 수에 비례해 늘리지 않는다.
- 콘솔 수동 설정은 ADR-0020이 이미 지적한 "복원 불가능" 문제를 그대로 안고 간다 — 인스턴스가 여러 대로 늘수록 그 위험도 커진다.

## 결과

**좋은 점**

- 웹 인스턴스 하나가 죽거나 재기동해도 나머지 한 대가 트래픽을 받는다 — 이전에는 인스턴스 자체가 단일 장애점이었다.
- 배포 실패가 "아직 손대지 않은 인스턴스는 무사하다"는 형태로 자연스럽게 무중단을 보장한다 — 블루-그린의 "전환 안 함" 안전장치와 결과는 같다.
- 배치·빗썸 피드가 트래픽 서빙과 분리된 인스턴스에서 돌아, 웹 인스턴스의 HTTP 처리 용량을 침범하지 않는다.
- 인프라 전체가 코드로 남아, 필요하면 `terraform apply` 한 번으로 동일하게 재현할 수 있다.

**받아들이는 대가**

- 웹 인스턴스가 2대라 EC2 비용이 늘어난다(스케줄러 1대까지 포함하면 이전 대비 3배).
- 롤링 배포는 블루-그린보다 배포 총 소요 시간이 길다 — 인스턴스를 한 대씩 순차로 처리하기 때문이다.
- 배포 도중(한 인스턴스가 새 버전, 다른 인스턴스가 이전 버전인 구간) 두 버전이 동시에 트래픽을 받는 짧은 창이 생긴다 — 블루-그린은 전환이 순간적이라 이 창이 없었다. API 하위 호환을 깨는 변경은 이 창을 감안해야 한다(기존 ADR-0021 §결정 7의 "파괴적 마이그레이션은 두 배포로 나눈다" 원칙과 같은 종류의 제약이 하나 늘었다고 보면 된다).
- `compose.bluegreen.yaml`은 더 이상 배포 경로가 아니지만 과거 기록·롤백 참고용으로 삭제하지 않고 남겨 둔다.

## 대안과 기각 사유

**(a) 인스턴스마다 blue/green을 복제해 타깃 그룹 4개로 관리한다**

기존 메커니즘을 그대로 확장하는 안. 그러나 타깃 그룹·가중치 조합이 인스턴스 수만큼 배로 늘어 관리 복잡도가 감당이 안 된다. 웹 인스턴스가 나중에 3대·4대로 늘면 이 복잡도는 선형이 아니라 더 가파르게 는다. 기각.

**(b) AWS CodeDeploy로 롤링·블루-그린을 관리형으로 위임한다**

블루-그린이든 롤링이든 관리형으로 얻을 수 있다. 그러나 CodeDeploy의 EC2 배포 모델은 ASG(오토스케일링 그룹) 기반 인스턴스 교체를 전제하는데, 이 저장소는 아직 ASG를 도입하지 않았고(ADR-0020 §6이 명시적으로 뒤로 미룬 결정) 지금 인스턴스 3대 규모에서 ASG까지 들이는 것은 과하다. 팀이 새로 익혀야 할 콘솔도 하나 는다. 다중 인스턴스가 상시 운영으로 자리잡고 규모가 더 커지면 재검토한다. 기각(현 시점).

**(c) 웹 인스턴스도 롤링 대신 한 번에 전부 교체한다**

가장 단순하다. 그러나 전부 동시에 내리는 순간 서비스가 완전히 죽는다 — 다중 인스턴스로 가는 목적(이중화) 자체를 배포 순간에 스스로 깨는 안이라 기각.

## 후속

- 실제 `terraform apply` 이후 확인할 것: 롤링 배포 총 소요 시간(웹 2대 순차 처리), 배포 도중 두 버전 공존 구간이 실사용에 문제가 되는지, ElastiCache 페일오버·RDS 재시작 시 EC2 쪽 재연결 동작.
- 오토스케일링(ASG) 전환은 인스턴스 규모가 더 커지는 시점에 재검토한다(위 대안 (b) 참고).
- SNS 알림 연동은 필요해지면 `alarm_actions` 변수에 토픽 ARN만 추가하면 된다.
